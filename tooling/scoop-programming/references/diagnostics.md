# 根据实际诊断定位错误

复杂调用报错、查询结果与预期不符或运行行为错误时阅读；普通编辑继续使用主 skill 的验证步骤。

## 编译错误

1. 先确认选择了整个 Cone 还是单文件、production 还是 tests、哪个目标与 sysroot。额外源码没有进入编译或测试依赖放错位置时，改表达式可能掩盖真正原因。
2. 查看主位置与关联位置，定位最内层已经确定的错误。`no applicable candidate` 可能只是外层调用失败的汇总，候选列表中的某一名义约束并不代表所有重载都要求它。
3. 对照实际声明核对参数顺序/类型、默认值、receiver、泛型约束、可见性与所有相关重载。扩展函数需要正确 import 和直接依赖；库已经安装或是传递依赖不能代替这两者。
4. 将复杂调用拆成有类型注解的局部 val，或在最小程序里保留出错的调用和实际声明。先修复内层参数，再检查外层；不要同时换 API、弱化断言并增加异常捕获，这会丢失定位依据。
5. 小程序与规范/声明仍冲突时，保留最小源码、工具链版本、完整诊断及命令报告编译器问题。临时绕行必须保持业务语义，不能把未经证实的限制写成语言事实。

| 现象 | 优先核对 |
| --- | --- |
| String 与 Option<String> 不匹配 | `T?` 是 Option<T>，存在值显式 Some；期望类型和安全调用的嵌套层数 |
| `assertEquals` 提示 Equals 约束失败 | 内层表达式是否已出错；名义与结构相等两个入口；actual/expected 的准确类型 |
| 同名方法/扩展不可见 | package/import、直接依赖、成员可见性、receiver 与约束；不能仅凭名称判断不存在 |
| 普通/挂起函数类型不匹配 | 是未定型字面量还是已定型函数值；是否需要 CoroutineScope 等 receiver；调用上下文是否允许挂起 |
| 测试能检查，生产程序失败 | `check --tests` 不验证生产 main；分别检查对应入口 |

编译诊断 JSON 在 stderr。该流还可能包含构建进度或外部工具日志，按实际协议读取记录，不把整个流当作一个 JSON 值。失败输出不能作为正常主题/API JSON 继续使用。

## 运行与集成错误

先区分编译/链接失败、程序非零退出、异常、错误结果和等待未结束。保留实际输入与输出，使用已有栈、调试信息或调试工具定位；前端检查通过不证明运行正确。

验证 CLI 标准流时先 `scoop build`，再直接执行生成的程序，分别捕获 stdout、stderr 和退出码。`scoop run` 的 stderr 还包含编译器进度，不能据此判断应用是否向错误流输出。

外部命令成功且输出为空仍是成功；非零退出、信号终止、启动失败和通信失败有不同含义。进程、文件或网络的测试替身保留这些区别，再用少量受控的真实集成验证管道与收尾。

先核对真实 TTY、服务监听、目标库和 native 资源等运行前提。缓存清理不会修复类型、import 或语义问题；不要将清空缓存、重建 sysroot 或换版本作为默认排错步骤。
