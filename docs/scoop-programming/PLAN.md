# Scoop AI 编程支持改进计划

日期：2026-11-12。状态：实施中，分批进展与验证见 [PROGRESS.md](PROGRESS.md)；维护采用配套的[标准更新工作流](UPDATE-WORKFLOW.md)。`scoop-lsp query`、`scoop api` 与 31 个完整示例主题已分别在 B5、B3 和 B2 实现；具体命令合同见对应工具文档。

## 1. 目标与范围

让 AI 能够发现并正确组合 Scoop 已有能力，设计合适的数据、模块、状态、错误与资源边界，并通过有效验证交付可维护的程序。编译通过只是其中一项条件。

本计划面向库开发、数据处理、文件与进程、命令行、异步网络及 UI 应用。`scoop-fetch` 的源码和 Agent 执行历史用于提供可复现的问题证据；它既不是统一架构模板，也不是唯一验收项目。其他领域的验收场景属于计划覆盖范围，不表示已对这些领域完成同等深度的缺陷审计。

继续使用现有编译器、文档模型、语言服务、Cone 测试和示例发布机制。新增能力必须对应明确的查询、诊断或应用需求；不另建语义检查器、通用应用框架、来源认证体系、资源计费系统或质量评分门禁。职责明确的小程序不强制拆层；接口、包装类型和公共抽象应有实际用途。

## 2. 已确认问题及改进方向

本次个案中，Agent 做过实际编译、测试和运行，并修正过运行结果。问题集中在反馈时机、材料的准确性与可发现性，以及验证所覆盖的行为。用户明确要求过抽象和 macOS 首个实现，因此不能把建立 provider 接口或尚无 Linux 实现本身算作缺陷。

| 编号 | 已确认的问题或缺口 | 通用改进方向 | 批次 |
| --- | --- | --- | --- |
| F01 | skill 仍称挂起 lambda 不由期望类型确定；API 风格文档仍使用 `String.length`，并将 `assertEquals` 描述为必须满足名义相等能力 | 对照规范、声明和实际程序修正文档；新增与修复能力同步移除旧限制 | B0、B7 |
| F02 | 示例检索 `process`、`terminal`、`environment`、`system` 均无结果；之后大量手工阅读源码 | 补领域入口、关键词及 API 查询；明确无示例不等于无 API | B2、B3 |
| F03 | 现有 skill 偏重语法与命令，缺少程序设计和实现后复审 | 增加数据建模、职责划分、状态、错误、资源及领域设计指导 | B1、B2 |
| F04 | 个案首次写入前阅读约 11 分钟，六个源文件约 623 行写完后才首次检查；随后三轮检查分别报告 7、1、30 个错误 | 先验证高风险 API 和一个可运行的最小功能，再按职责扩展；记录反馈成本，不设置任意代码量或时间配额 | B1、B7 |
| F05 | 数量、时长等过早格式化为字符串；采集、解释、计算和展示混杂；渲染器保留平台专用 logo | 保留有业务意义的类型和单位；将可变展示数据显式传入，在适当边界格式化 | B1、B2 |
| F06 | 通用命令封装将多种异常、信号、非零退出、空输出折叠；成功且为空的结果被当成缺失 | 保留实际错误及结果信息，由应用决定降级；测试零值、空值、缺失与失败的区别 | B1、B2、B6 |
| F07 | 备用命令在主要结果存在时仍执行；已有 `Option.orElse` 等组合函数没有被发现 | 展示惰性组合与调用次数验证，避免用急切求值的实参表达 fallback | B1、B2、B3 |
| F08 | 嵌套调用参数类型错误产生外层泛型候选噪声，Agent 错判为 `assertEquals` 不支持 Option，继而降低断言质量 | 改善原因定位；先缩小复现并核对重载，再决定修改程序或报告编译器问题 | B1、B4 |
| F09 | CLI 官方示例与个案都把用法错误写入 stdout；示例测试也固定了该输出 | 同步修正源码、正文和测试，独立验证 stdout、stderr 与退出码 | B0、B2 |
| F10 | 测试验证了实现自己的假设，未发现多余调用、错误分类、Unicode 列宽等问题 | 按需求和边界构造独立输入；保留期望/实际值，覆盖副作用及必要的真实集成 | B1、B2、B7 |
| F11 | `charLength` 被用作终端列宽；解析外部命令时依赖人类可读文本 | 说明文本单位与平台边界；复用字符集能力，优先使用真实可用的机器可读输出 | B1、B2、B6 |
| F12 | 文档模型已有签名、receiver、约束等信息，终端仍缺少面向 AI 的完整 API 查询 | 从现有模型发布可查询数据，不抓取 HTML 或重新解析语言语义 | B3 |
| F13 | LSP 已有补全、签名、导航等能力，但当前 Agent 路径主要依赖 shell 阅读和整项目检查 | 提供薄的命令行语言服务入口，复用现有语义实现 | B5 |
| F14 | 同步进程 `communicate` 无超时合同；应用难以可靠限制外部命令等待 | 补有明确收尾责任的进程通信截止时间能力 | B6 |
| F15 | 缺少编译器/内置库变更后统一同步 skill、示例、工具和发布包的维护流程 | 建立按影响范围更新、验证、打包和反馈的标准工作流 | B0、B7 |

F08 已通过最小程序确认：当 `optional` 的参数为 `String?` 时，`assertEquals(Some("x"), optional("x"))` 会产生误导性的候选错误；将内层调用修正为 `optional(Some("x"))` 后，原 `assertEquals` 可以编译并通过 Cone 测试。现有测试库已提供结构相等重载，无需再增加 Option 专用断言或改变语言的可空转换规则。

相关现有入口：[skill](../../tooling/scoop-programming/SKILL.md)、[语言参考](../../tooling/scoop-programming/references/language.md)、[API 风格](../specs/SCOOP-API-STYLE.md)、[Option 实现](../../sysroot/src/scoop.std/src/results/option.scoop)、[相等断言](../../sysroot/src/scoop.test/src/equality.scoop)。

## 3. 实施顺序与交付

P0 表示先消除错误指导并改善当前开发路径；P1 表示补齐查询和诊断；P2 表示接入更多已有语义能力及补库缺口。优先级不代替依赖关系，也不要求等待所有批次完成后才交付前面的改进。

| 批次 | 优先级 | 交付 | 前置条件 |
| --- | --- | --- | --- |
| B0 | P0 | 修正文档与错误示例，启用标准更新工作流 | 无 |
| B1 | P0 | 通用设计、开发、调试和复审流程进入 skill | B0 的规则核实 |
| B2 | P0/P1 | 领域示例、可发现性和有效的示例验证 | 基础修正先做；综合示例采用 B1 |
| B3 | P1 | API 数据发布及终端查询 | 先定义查询合同；复用现有文档模型 |
| B4 | P1 | 根因明确的编译诊断和可用导入提示 | 使用本次最小复现；可独立于 B3 实施 |
| B5 | P1，优先于 B3 | 面向 Agent 的语言服务命令行入口 | 复用现有 LSP；不以新语义引擎为前提 |
| B6 | P2 | 进程通信超时及经实例确认的库易用性修正 | 各项先修订对应领域规范 |
| B7 | 贯穿各批 | 多领域 Agent 验收、更新流程验证与简明结果记录 | B1/B2 后先做一轮，新增能力逐批加入 |

每批按“规范或合同 → 实现与材料 → 必要验证”交付。新增命令、API、主题只有在配套工具链可用后才进入 skill 的正式用法；等待期间保留当前可行的查询路径。

## 4. B0：修正事实与建立维护入口

1. 修正挂起 lambda 的表述：未定型的字面量按期望类型确定挂起性；已定型的普通函数值不会自动变为挂起函数值。保留显式 `suspend` 的正确用法，说明两者区别。
2. 核对 `String.charLength`、值类型相等和泛型断言的实际规则，同步修正语言参考与 API 风格文档。分别说明 `==`、名义 conformance 和 `where requires`，不把某个重载的要求写成整个库的限制。
3. 将 `cli/options` 的用法错误写到公开标准错误流，帮助和正常结果仍按 CLI 合同输出；同步修正文案与现有外部验证。具体写入 API 以当前声明为准。
4. 使用[标准更新工作流](UPDATE-WORKFLOW.md)整理本次受影响条目，并在仓库工作流约定、tooling 和示例维护说明中提供入口，使编译器/库维护者也能发现同步要求。直接修改失效表述，不无限追加历史注意事项。

改动位置：`tooling/scoop-programming/references/`、`docs/specs/SCOOP-API-STYLE.md`、`sysroot/src/scoop.cli/examples/greet.scoop`、`sysroot/share/scoop/examples/topics/cli/options.md`、`tooling/scoop-example/tests/run_examples.py`。

验收：相关正确写法由发布示例或 Cone 测试验证；真正非法的类型转换仍失败。CLI 用法错误退出 2、正文在 stderr、stdout 为空。修正文档与实现冲突时先处理对应规范，不借机改变未涉及的语言规则。

## 5. B1：让 skill 引导设计与短反馈开发

### 内容组织

`SKILL.md` 保持为简短工作流和材料导航，新增按需阅读的设计参考，扩展现有库与工具参考。长签名和完整程序继续由 API 文档、源码及示例提供。首次接触语言读取核心差异；后续修改只加载本次涉及的规则和领域材料。

按任务路由材料：库与数据处理侧重类型、泛型、可见性及稳定 API；文件/进程侧重结果与资源；异步网络侧重任务、取消和连接生命周期；UI 侧重状态、事件、身份与布局。小脚本无需先读完整 UI、FFI 或 runtime 文档。

### 通用设计指导

| 设计问题 | skill 应提供的判断方法 |
| --- | --- |
| 数据形状 | 区分原始输入、领域数据和展示数据；数量、单位、状态保留到使用它们的边界。纯展示 DTO 可以持有字符串，但不能因此丢失后续计算需要的信息 |
| 状态与复制 | 用 struct/enum 表达值和状态变体，用 class 表达确需共享的可变状态或身份；说明浅快照、引用字段、闭包捕获及并发同步责任 |
| 模块与公共 API | 依据真实职责和变化原因拆分；公开接口最小化，核对 Cone 边界及构造器/成员可见性；测试不成为公开本应内部实现的理由 |
| 抽象 | 平台差异、已有多个实现或测试所需 I/O 替换可以使用接口；简单纯函数和数据参数足够时采用它们，不为所有类增加接口 |
| 缺失与失败 | 区分零值、空集合、空文本、缺失、解析失败、系统错误和取消；按实际 API 选择 Option、Result 或异常，由上层决定哪些结果可降级 |
| 组合与求值 | 先查询 `map`、`flatMap`、`fold`、`getOrElse`、`orElse` 及 Result 转换；识别实参急切求值和回调惰性求值，避免多余 I/O |
| 资源与异步 | 标明创建者、借用者和关闭责任；使用现有 `use`/异步作用域，取消后等待收尾；不把 `suspend` 当成并行或把 sleep 当成同步 |
| 外部边界 | argv 逐项传递，保留退出状态和 stderr；机器可读输出可用时优先使用，解析时遵守实际格式和单位；正常输出、诊断、日志各按接口合同处理 |
| 展示与 UI | 平台标识和主题作为实际所需的数据输入；区分字节、标量、字素簇、终端列宽；UI 事件使用执行时的状态，遵守现有 key、Binding 和组件生命周期 |

领域规则来自[API 风格](../specs/SCOOP-API-STYLE.md)及对应规范。将其转成简短的使用指导，不要求应用作者读完整编译器规范，也不把全部建议实现成编译器 lint。

### 开发、调试与复审流程

1. 阅读任务和现有项目，确定输入、输出、关键类型、外部依赖与失败行为。对简单任务用简短说明即可，不强制先写设计文档。
2. 查询相关示例和实际 API，针对最不确定的语言/API 组合编译小程序或最小功能路径。未找到示例时继续查文档和声明，不宣布能力不存在。
3. 建立可运行的最小功能，再按职责扩展；一批修改后先格式化，再检查和运行相关测试，避免将不确定规则复制到整个项目。
4. 遇到意外诊断，先核对内层表达式、参数类型、receiver、import、直接依赖和全部重载；缩小复现，再判断是代码、文档还是编译器问题。保留精确断言，不能仅因诊断难懂就改成 `assertTrue` 或吞掉异常。
5. 编译修复后重新审阅设计：是否增加了无意义的 Option 包装、重复分支或不必要的可变状态，是否过早格式化、重复 I/O、遗漏收尾，测试是否仅重复实现假设。
6. 根据实际功能运行必要的端到端验证；编译诊断 JSON 从 stderr 读取，与程序 stdout 分开处理。运行失败依据实际退出状态、栈和错误输出，按需使用已有调试工具定位；性能问题采用 release 测量和可解释的调用次数。交付说明区分语义检查、构建、测试和真实运行，未执行的验证不写成通过。

验收：用数据处理库和文件/进程应用检验这条流程，能在大规模实现前验证关键 API；设计理由、测试覆盖与最终代码一致。收益通过 B7 观察，不能仅凭 skill 文本变长宣称改善。

## 6. B2：完善示例、检索与示例验证

### 内容顺序

优先扩展已有主题，再补实际缺失的完整例子。以下新增名称为工作名，发布时统一确定。

| 内容 | 依托入口 | 必须展示的行为 |
| --- | --- | --- |
| Option 与 Result 组合 | `language/option`、`language/errors` | 映射、展平、保留错误、惰性 fallback；空值与缺失不同；回调调用次数有断言 |
| 准确的断言 | `test/assertions` | Option、普通值类型及结构相等；失败保留 expected/actual 与位置；不复制库已提供的断言 |
| 公共库及消费者 | `language/visibility`、`language/generics` | 可用的公共签名、构造器/成员可见性、依赖与 import、独立消费者和所属 Cone 测试 |
| 文件和进程 | `io/files`、拟新增 `io/processes`、`io/environment` | 成功且为空、非零退出、启动失败、stdin/stdout/stderr、资源关闭；超时能力仅在 B6 完成后加入 |
| CLI 与终端 | `cli/options`、拟新增 `terminal/output` | 正常/错误流、帮助与退出码、重定向、颜色选择、Unicode 和窄终端的明确降级策略 |
| 有实际职责边界的应用 | 拟新增文件报告等多文件主题 | 解析、领域计算、I/O 与展示的必要分离，合理测试替身；不照搬系统信息查询器或强制层数 |
| 异步网络 | `async/tasks`、`http/get` | 正常请求、失败、取消、等待收尾和响应资源；使用本地可控服务，复用当前公开 API |
| 有状态 UI | 复用现有 UI 库例子形成入口 | 状态更新、事件时机、稳定身份、组件卸载与资源收尾；真实支持的目标上运行 |

示例是可读的完整程序，说明四节继续使用“运行、预期结果、关键说明、常见误用”。教学程序存一份源码；能复用库例子的直接引用原文件。相关主题、源文件、依赖与运行条件在注册前全部有效。

### 查询和验证改进

1. 为库名、API 名、receiver、英文/中文领域词补充有真实内容对应的关键词与别名。查询结果说明匹配原因，正文说明不覆盖哪些能力；不通过给所有主题添加宽泛关键词制造命中。
2. `scoop example` 继续检索示例元数据。无结果时给出查看分类、缩短关键词和查询 API 的准确下一步；B3 发布前只提示现有文档/源码路径。
3. 改进现有 `run_examples.py`，利用 `subprocess.CompletedProcess` 等现成结果保留 stdout、stderr 和退出状态，并更新实际调用方。日志可以合并保存，但断言不能混淆流。
4. 普通行为放在示例所属或配套 Cone 的 `scoop.test` 中；示例 runner 负责文件还原、正式 CLI、进程协调与运行前提，不再用逐个冷/热构建替代 API 覆盖。
5. 编译失败规则放入代表性的 expected-error fixture，断言主位置和信息；不要为每个库重复相同的类型错误规则。示例的错误演示引用这些规则或用简短说明，不让发布的可运行主题无法运行。

改动位置：[示例索引](../../sysroot/share/scoop/examples/catalog.toml)、`topics/`、`programs/`、相关库 `examples/` 与 `tests/`、[阅读器](../../tooling/scoop-example/README.md)、[示例设计](../scoop-example/DESIGN.md)及主题清单。

验收：从实际 `--format json` 输出还原完整文件集合，按正文命令在同一工具链运行；发布索引只包含完成项。进程、环境、终端等查询能到达准确材料。普通验证使用 release、共享已准备的 sysroot 和 Cone cache。

## 7. B3：发布可供 AI 使用的 API 查询

### 数据和命令

拟提供 `scoop api search` 与 `scoop api show`，支持可读文本及 JSON。它们回答“有哪些 API、声明是什么、从哪里导入”；当前位置的类型与可调用性由 B5 的语言服务回答。

直接复用 [ConeInput/ApiItem](../../compiler/doc/src/model.rs)、公开 binding 和文档生成流程。现有[站点搜索](../../compiler/doc/src/render/search.rs)主要保存摘要与 URL，不能作为完整 API 签名接口。为文档发布增加必要的机器可读输出，不把私有文档缓存格式变成公共 API，不从 HTML 反解析类型信息。

查询至少包含：

- 搜索：名称、所属库/package、receiver、摘要和经过维护的领域词；有歧义时返回候选，不猜测唯一答案。
- 详情：真实签名及全部相关重载、泛型约束、扩展 receiver、可见性、可用导入/re-export、依赖坐标及目标条件。
- 使用信息：普通/挂起函数类型、文档中的异常与资源责任、相关示例和源码位置；缺失的行为说明标为未记录，不从命名推断事实。
- 机器合同：明确成功、无匹配和输入/读取错误，保持 stdout 数据与 stderr 诊断分离，返回实际结果种类和必要的格式版本。

`SymbolKey` 等文档键仍是展示地址，不替代语言内部的类型化实体 id。库在文档中出现不等于已进入当前项目的直接依赖；查询结果应提示这个区别。

### 实施与验收

先在[实现规范](../specs/SCOOP-IMPL-SPEC.md)相关 CLI/文档条款和工具设计中确定发布位置、目标选择、查询参数与输出合同，再实现数据导出及独立阅读器。文档/API 数据在原有构建或安装文档生成步骤中更新；查询不隐式构建、安装、下载、清缓存或审计生成过程。

覆盖 `Option.orElse`、`Result`、`assertEquals` 两类约束、扩展函数、公开 re-export、同名重载、不同目标及缺失文档。接口重命名后，重新生成的数据反映当前 API，不靠保留旧接口兼容别名掩盖迁移。

包与安装验证复用 [scripts](../../scripts/README.md) 的现有布局测试；输入未变时复用既有文档结果，不增加缓存命中内容重验。B3 完成后再同步 skill 的查询顺序和无匹配提示。

## 8. B4：让诊断支持正确修复

1. 以 F08 的坏/好程序为第一组回归，保留内层参数类型错误的位置和原因。区分独立根因与依赖某个候选的失败说明，避免外层名义约束消息淹没已确定的内层错误。
2. 对缺失扩展方法或名称，使用当前 Cone、直接依赖、可见性和 receiver 约束中的真实信息给出提示。能准确确定 import 时提供修复；多个合法候选则列出选择，不自动挑选，不把缺少依赖一律诊断成缺少 import。
3. 人类输出、JSON 和 LSP 保持主诊断、关联位置与原因一致。只增加解决这些问题需要的诊断结构；继续复用前端求解结果，不在输出层重跑语义检查。
4. 对 Option 嵌套、安全调用、smart cast 误用、实际泛型约束失败和导入歧义增加必要代表用例，防止通过删除候选信息或隐藏其他真实错误让单例“变干净”。

改动入口：`compiler/hir-lower/src/overload/diagnostics.rs` 及调用解析诊断，`compiler/source`、`compiler/protocol` 的诊断表示，CLI/LSP 展示与现有 code actions。遵守[语言服务设计](../language-service/DESIGN.md)和现有诊断合同。

验收：F08 坏例指向真正的参数问题，好例继续使用原有 `assertEquals`；独立的真实约束错误仍得到约束诊断。自动修复不引入非法 import，也不擅自将普通值包装为 `Some`。面向 Agent 的小任务能依据诊断修复原调用，而不是撤换有效库 API。

## 9. B5：把已有语言服务接到 Agent 的工作路径

采用 `scoop-lsp query` 作为命令行入口，通过现有 LSP 访问诊断、补全、签名、hover、定义、引用等能力，合同见[语言服务 CLI](../language-service/CLI.md)。按用户的后续要求，此批优先于独立 API 索引，并先用于后续示例开发和 AI 评测。先提供这些读取能力，再按实际需求暴露已有重命名和 code actions 的编辑结果。

复用 `compiler/lsp` 和 `compiler/analysis` 的 workspace、snapshot、位置转换、取消及版本处理。使用现有 stdio 传输，不建立另一套语义数据库、常驻服务框架或强制特定 Agent/MCP 客户端。

明确项目根、目标、生产/测试 purpose、文件和位置编码，以及磁盘内容或显式临时正文的选择。结果区分无匹配、部分可用和请求失败；不完整源码仍返回已可确定的信息。跨文件编辑附带源版本信息，由调用方按正常编辑流程应用。

能力清单只声明实际支持的方法。依赖解析沿用现有语言服务/包管理器合同；不能把当前缺少 lock 时的解析描述为始终离线，也不新增隐式 sysroot 构建和缓存清理。

验收：跨 Cone 定义、扩展补全、嵌套泛型签名、非 ASCII 位置、错误源码和文件更新能通过终端查询；同一源码位置与现有 LSP 客户端一致。所有新增路径调用同一语义实现，普通应用开发不依赖 LLVM 仓库开发环境。

## 10. B6：补真实的库易用性缺口

### 进程通信截止时间

当前[平台规范 §11](../specs/SCOOP-PLATFORM-SPEC.md)规定 `communicate` 不承诺超时，`close` 也不隐式终止进程。应先设计可选超时/截止时间参数和超时结果，再实现各平台，不把现有阻塞调用简单包在无法收尾的线程里。

合同覆盖整个 stdin 写入、stdout/stderr 排空和等待阶段，使用单调时间。明确负值/零值、已经退出与刚好到期的竞争、部分输出、原始 I/O 错误与清理错误，以及返回前关闭端点、终止并回收本次负责 child 的责任。后代继承 pipe 的 EOF 延迟也必须有明确处理，不能令有限等待再次陷入无限 read/join。

范围限于当前 ChildProcess 拥有的进程和端点，不扩展成进程树管理器。需要 native 修改时只修改实际相关的库 bridge 与合同，不无故进入全局 runtime ABI。

验收使用受控子进程覆盖：正常退出、成功空输出、非零退出、启动失败、大量双向管道数据、到期收尾和后代持有 pipe。外部进程控制使用对应 fixture；可直接测试的值和错误行为使用 Cone 测试。按实际支持目标验证平台实现，不把单平台结果写成跨平台完成。

### 其他库改进的边界

- 先补现有 API 的可发现性与文档。已有 Option/Result 组合和结构相等断言不新增平行实现。
- 文本宽度已有 [graphemes/unicodeScalarWidth](../../sysroot/src/scoop.charset/src/unicode.scoop) 及 [readline 布局实现](../../sysroot/src/scoop.readline/src/render/layout.scoop)。整理其单位、控制字符和 emoji 策略；标量宽度相加不能自动成为字素簇列宽。只有出现真实的公共复用需求时才提取共同 helper。
- 外部命令访问示例优先查询真实可用的机器可读格式，减少重复启动和重复扫描；不要仅因一个应用需求就建设整套硬件信息库。
- 其他领域发现 API 缺口时，先给出真实调用、现有能力不足的复现、最小新增合同和验收，再进入相应库计划。此项不授权统一重写所有内置库。

## 11. B7：多领域效果验收与持续维护

### 任务集与评价方法

B1/B2 后开展第一轮对照，B3–B6 分别加入对应能力。任务应含新建和修改已有项目，不能全是照抄示例的题目。保留部分未直接示范的组合，检验指导能否迁移。

| 任务类别 | 要观察的质量 | 必要独立验证 |
| --- | --- | --- |
| 库与消费者 | 值语义、泛型、公共边界、准确依赖和 import | 独立消费者、引用字段/快照行为、错误路径和断言质量 |
| 数据处理 | 解析/计算/展示边界，Option/Result，数值和单位 | 外部给定的输入/期望，空与缺失、无效数据、边界数值、Unicode |
| CLI、文件与进程 | 输出合同、资源责任、可替换 I/O、惰性 fallback | 分离标准流、退出码、真实命令失败、调用次数和临时资源收尾 |
| 异步网络 | 并发与挂起区别、取消传播、资源关闭 | 本地可控服务、失败/取消后收尾、响应资源处理 |
| 有状态 UI | 状态所有权、事件时机、key、合理函数拆分 | 更新及重复事件、列表变化/卸载、可运行目标上的实际界面行为 |

`scoop-fetch` 可以作为 CLI/进程类别的历史对照；不要求把其所有平台功能实现完，也不把改造该仓库列为本计划完成的前提。

固定任务要求、工具链与可用材料；对照时尽量保持模型和设置一致，并记录未控制的差异。少量重复运行用于区分偶然性，不从一次成功推断模型总体质量。不得只比较“编译通过率”或测试个数。

记录首次有效验证时间、查询是否命中、源码阅读范围、诊断后的修复是否正确、无必要 workaround、错误/资源/副作用测试以及设计复审发现。它们用于比较，不构成 CPU、内存、token 或代码长度的配额。验收依据是明确行为与可维护性，避免强制某个文件数或唯一架构。

由维护者按需求准备独立输入和期望；不全部采用 Agent 根据自己的实现生成的测试。原始会话、命令日志和逐次报告保存在仓库外，仓库只保留任务范围、结果概要、残留问题和工具链信息。

### 标准更新工作流落地

配套 [UPDATE-WORKFLOW.md](UPDATE-WORKFLOW.md) 规定变更分类、同步对象、顺序、验证、发行包检查和精简交付记录。B0 起即可使用；新增 API 查询和语言服务客户端落地后，再启用其中对应步骤。

选取一次语言规则/诊断修复和一次内置库 API 变更实走该流程，验证：旧表述被替换，实际消费者迁移，示例从安装材料可还原运行，查询结果/帮助对应当前能力，包中 skill 的相对引用完整。内部实现重构若不影响外部使用，应能明确跳过材料更新。

## 12. 验证职责与完成标准

各批使用[标准更新工作流](UPDATE-WORKFLOW.md)中的命令和仓库现有测试入口。Rust/Python/Scoop 修改先执行相应格式化与 lint，再测试。普通行为使用所属 Cone 的 release 测试；诊断、CLI、产物及外部进程合同采用适当 fixture。编译器变更完成要求的 Rust 与正式 CLI 覆盖，不能用 `cargo test` 替代文件 fixture 验收。

普通验证消费已准备的目标库与共享缓存，不为每个例子重建系统库，不通过删除或隐藏源码/工具验证缓存，不开启无关的 GC stress。通过相关检查后，只因新修改、失败或未解决的风险追加验证。

本计划完成时应具备：

1. 已知错误指导与示例输出问题修复，正确规则有可运行示例或必要回归。
2. skill 能引导跨领域设计、API 查询、小步验证、诊断定位及编译修复后的复审。
3. 示例与 API 查询相互导流，完整签名和已有组合能力容易发现；Agent 能使用当前项目的真实语言服务结果。
4. 已确认的诊断和进程等待缺口按各自合同闭合，无重复语义实现或无依据的库扩张。
5. 多领域任务验证行为和代码质量改善，记录残留限制；标准更新工作流随实际编译器/库更新走通。
