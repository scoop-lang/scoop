# Scoop AI 编程支持：Agent 验收记录

日期：2026-11-12。对应[改进计划](PLAN.md)、[实施进展](PROGRESS.md)和[标准更新工作流](UPDATE-WORKFLOW.md)。原始会话、输入、日志与逐次 JSON 留在仓库外；本文只记录任务、结果、可解释的观察和限制。

数据处理、公共库、CLI/进程、异步网络和 UI 的独立验证已经完成。UI 包括状态测试、生产构建和用户解锁后的真实窗口交互。交互结果来自操作后的可见状态及关闭后的进程观察，不能将模型自报成功、编译通过或静态截图当作交互通过。

## 1. 任务与运行条件

任务包含新建程序和修改已有项目；库的深快照/泛型查找、进程按退出状态选择备用命令、网络失败取消兄弟任务，以及 UI 的过滤/撤销组合，均不是要求逐字还原发布示例。原有 scoop-fetch 继续作为历史问题证据，没有改写它来充当唯一验收。

所有应用样本在 macOS/AArch64 上运行。旧数据样本使用原 skill 快照和原安装工具链；更新后的数据/库样本使用 B4 配套开发工具链，进程/网络/UI 样本加入 B6 的库与材料。数值复审样本使用后续 B7 指导，并启动新的 Agent 进程。工具链和材料并非全部固定，因此不能把用时差异单独归因于 skill。

## 2. 独立验证覆盖了什么

**数据处理。** 初始两轮使用相同七组外部输入：正常统计、空文件、负数、后段非法记录、CRLF/排序、缺文件、缺参数。两者均保留数值模型和独立渲染，原材料没有必然产生坏结构。补充相同数值输入后，单条 Long.MAX_VALUE 和不可表示的单字段均处理正确，但 Long.MAX_VALUE 与 1 的同组汇总都输出负数且退出 0。

后续复审在独立副本上进行，原失败样本保持原样。修复只涉及统计函数、其契约注释和必要测试。维护者另验十二组输入，包含最大值加零、不同任务各自达到最大值、同任务汇总溢出，以及原有正常/错误边界；错误时 stdout 为空，最大合法结果保持准确。

**库与消费者。** 种子库只复制集合，仍共享可变 Reading。独立消费者验证修改原对象、清空/增加原集合均不影响快照，公开集合不能作为 MutableList 修改，条目使用不可变值；同时验证不具备 equals 的类型可参与泛型查找、首次命中即停止、缺失返回 None、空输入合法、负数/重复 id/总数溢出拒绝。结果结构与用途相称，公共 API 的行为注释仍不充分。

**CLI/文件/进程。** 独立 Python 子进程记录实际调用角色与 pid。验证空成功不触发备用命令，只有退出 3 才调用备用命令一次；中文、空 argv 和含空格路径保持逐项传递。启动失败、退出 7、信号 15、primary/fallback 超时均保持所需状态与 stderr，错误 stdout 为空，拥有的子进程没有留在后台。配置中的未使用分支也在启动前完整验证。二十组检查全部通过。

**异步网络。** 独立服务在两个请求都到达后才允许响应，不以固定 sleep 推断并发。正常结果按输入顺序编码，空正文成功。503、连接中断、超限正文、非法 UTF-8 均产生带失败 URL 的诊断；另一连接分别停在响应头之前和部分正文之后，并交换输入顺序。程序返回前，服务实际观察到未完成连接关闭；stdout 没有提前发布部分结果。十组检查全部通过。实现使用已有 coroutineScope/HttpClient/response 作用域，无自建调度器。

**UI。** 独立副本验证过滤只改变可见项、Reverse 作用于完整列表、身份和计数保留，删除后增加再撤销能恢复原对象与位置，重复撤销不复制条目，Reset all 更新全部模型，新增不复用已删除 id。三组组合测试通过，生产源码独立构建成功。

UI Agent 为原生输入测试加入了指向本机 `current-sysroot/.../scoop.window/test-native` 的路径依赖，随后长时间等待原生键盘/焦点事件；维护者停止了该轮继续扩展测试。之后原生 GUI 工具明确报告 Mac 锁屏且自动解锁失败。这个环境事实可能影响焦点与输入，不能据等待现象断言 UI 库或应用有缺陷。

用户解锁后，维护者复用该样本独立构建的生产二进制，用临时 macOS 应用包供 GUI 工具定位窗口，没有修改样本源码。实际点击确认：Counter 1 连续两次加值后为 2；非零筛选只显示该项，重排完整列表后显示顺序为 2、1，计数仍保留；删除 1、新增 3、撤销删除后顺序为 2、1、3，原计数恢复，第二次撤销不复制条目；全部重置后非零筛选为空，显示全部时三个计数均为零。Cmd+I 新增编号 4。最后通过系统标题栏菜单的 Close Window 关闭，窗口消失且对应进程退出。这是本轮样本的维护者交互验证，不替换原 Agent 人工中止的记录，也不以旧 B2 示例的结果代替。

## 3. 对材料和工具的实际反馈

更新后的数据样本有九次包含 API 查询的 shell 调用，直接 Read 从十二次降为四次。首次成功 check 从约 695 秒提前至约 446 秒；这些是本次样本的观察，不是统计效果或固定收益。进程、库与 UI 样本也使用了 API 查询，网络样本仍较多读取源码。没有通过强制某个文件数或抽象层数评价程序。

这些 Kimi 应用样本均未主动调用 `scoop-lsp query`。语言服务 CLI 的正确性由正式 stdio 对照 fixture、相关 Rust 测试和 OpenCode/DeepSeek V4.1 Flash 1017 的小型修复样本支持；后者约 226 秒完成并通过独立检查，仅作参考。不能据此宣称已经测得 LSP 在 Kimi 普通任务中的自然采用率或收益。

两项新增问题进入计划并在材料中处理：

- **F16：输入合法不保证计算合法。** 语言参考明确整数回绕；设计复审检查汇总和单位换算。现有 test/assertions 主题增加非负毫秒汇总及最大值、负值、超界测试，从发布 JSON 还原后八项 Cone 测试通过。未修改语言算术语义，也没有建立通用配额系统。新启动的 K3 复审样本修复了真实缺陷并通过独立验证；因任务也明确要求数值准确，不能把成功完全归因于新增文案。
- **F17：验证方式与依赖边界。** 设计参考和 ui/state 正文区分纯模型、公开宿主生命周期与真实 GUI 输入；测试支持须有可用发布接口和可重建来源，不能把本机开发安装的路径当成项目通用依赖。原生输入未完成时记录环境和实际验证范围，不通过 idle 次数或截图宣称交互完成。本次尚未重跑完整 UI Agent 样本来衡量这一指导的效果。

另外，复审步骤补充公共 API 注释中的单位、失败和所有权；CLI 验证直接用公开的 `-o` 选择可执行文件位置，减少读取内部构建记录的绕行。

## 4. 更新流程验证与剩余事项

B4 的 F08/import 诊断和 B6 的 communicate 超时分别实走编译器诊断与库 API 更新流程：先修订合同，再改实现、调用方、发布示例、检索词、API 数据、skill 和相关验证。B6 同时发现并补齐 runtime_builder 的独立 Cargo.lock，保留 --locked；四个未变化 runtime 得到复用。详细平台范围见 PROGRESS。

新增 skill 已同步至 Kimi 及开发安装目录，使用新进程做数值复审。测试目标、临时服务、跨平台验证副本和临时 macOS 应用包已按需清理；原始会话、必要结果、评测源码及共享工具链资源留在仓库外。

本轮计划验收已完成。结论仍受样本数量限制，不能据此证明通用质量提升，材料也不能保证所有模型遵循工作流；这些限制不是增加统一评分门禁或无限重复评测的理由。平台范围及既有前端测试失败继续按 PROGRESS 如实记录。
