# UI 交互打磨与 accessibility 实施计划

日期：2026-11-18。状态：accessibility 领域的整批实现与 macOS 定向验证完成，继续一级剩余交互功能；实际交付与平台验证见[实施记录](PROGRESS.md)。

本计划统一安排[交互打磨设计](DESIGN.md)与[accessibility 设计](../accessibility/DESIGN.md)的实现、消费者迁移和验收。两份设计规定行为与技术边界，本文规定任务拆分、依赖、交付顺序和完成条件；设计中的 U0～U5、P0～P5 仅作为来源分组对照，后续按本文记录实施状态。

目标是在当前桌面 GUI 平台上形成完整可用的交互与无障碍能力：macOS、Windows、Linux GNU 的 Wayland／X11。沿用普通 Scoop Cone、既有 owner、场景提交、文本模型和 native 后端；不增加 UI 专用编译器／runtime 机制。accessibility 沿用 C／Objective-C／C++ 选型，不新增 Rust 依赖或采用 AccessKit；App Intents 与 Swift 互操作维持独立后续范围。

## 当前待办与执行顺序

先补功能缺口，再完成三个平台的功能验证，最后处理配色；S0～S11 是范围索引，不要求逐小项切换开发和测试。**accessibility 已按整个领域完成实现与本地集中验证；下一领域是触摸／手势，完成其全部功能缺口后再集中测试。**

### 按领域开发与验证

以开发效率为首要目标。accessibility、触摸／手势、动画及其余交互分别按完整领域推进：先完成该领域全部已知功能实现与必要的规范／消费者更新，再统一构建和执行该领域测试。每轮测试汇总全部已发现缺陷，完成这些缺陷的修复后才进入下一轮；不再为单个接口或单个控件反复执行整条依赖构建和回归。开发中的格式化与源码核对正常进行，已有通过且输入未变的结果复用。

accessibility 本轮实现队列覆盖 S2／S4／S5／S7／S10／S11 的相关功能：集合状态及行列／层级／活动项关系；文本保留范围、表单状态与公告；控件默认语义、实际操作及模态边界；AppKit、Windows UIA、Linux AT-SPI 的对应能力。测试准备可随实现补齐，但功能实现齐备前不启动测试轮次。手势和动画继续沿同一节奏，配色仍在全部功能及三平台验证之后。

## 2. 执行规则

1. 每批先更新对应 spec，确定正式签名、默认值、平台能力、错误与生命周期，再修改实现、builder、调用方、必要示例及受影响的 skill／API 材料；S11 做整体核对，不把使用材料的更新推迟到最后。项目未发布，直接迁移当前接口，不保留兼容别名或双轨实现。
2. 已具备的多击选择、轴向 Drag、文本编辑、菜单角色、焦点、虚拟化和动画作为复用基础。以实际缺口修改，不重复建编辑模型、输入树、时钟或业务状态。
3. accessibility 从 S0／S2 开始，文本、滚动、拖放、触摸在自己的批次中接入已具备的语义能力；不能把所有 provider 工作集中到最后。
4. 依赖表示相关接口或原型结论已具备，不要求等待同一批次中无关平台和任务。一个平台的局部问题只阻塞依赖它的工作；三平台核心交付的未完成状态必须保留。
5. 按完整领域收齐实现、消费者、测试源码与材料，再统一格式化、lint／check 和定向测试；每轮收集全部已发现缺陷，集中修完后开始下一轮。普通库行为用所属 Cone 的 release 测试；只在真实 CLI、ABI、产物或外部进程合同需要时使用 fixture。
6. 批次完成包含规范、实现、实际消费者和必要验证。实现已写但 native／设备验证未做，应分别记录；文档完成、构建通过或检查器能显示节点均不能替代交互验收。
7. 实施状态记录批次、实际目标、通过范围、未闭合问题和下一步。原始日志、截图批次和逐次报告放仓库外，不生成重复的验收归档。
8. 验证限于本次实际变更，复用输入未变化的已通过结果。系统前台激活策略造成的焦点获取限制记录为环境条件，不反复启动窗口、调整激活或等待脚本、要求人工聚焦，也不阻塞无关变更交付；只有实际涉及焦点行为的变更才安排相应的定向检查。
9. 严格遵守顶部待办的一级 → 二级 → 三级顺序。每批提交、推送并合并 `origin/main` 后，继续当前最高未完成级别；会话恢复或上下文压缩也不改变这一约束。

## 4. 批次任务与完成条件

### S0 环境、平台能力和原生边界

**交付：** 可复用的基线场景、必要原型、平台能力与返回合同结论。

| 子项 | 工作 | 必须取得的结果 |
| --- | --- | --- |
| S0.1 基线与设备 | 固定当前源码／工具链，确认开发 sysroot 和目标预编译资源；选择现有编辑、滚动、拖动、菜单、虚拟列表测试及展示入口；确认触屏、触控板、辅助技术和外部拖放程序 | 记录真实目标、设备与基线结果；设备缺失列为待验证，不记为不适用或通过 |
| S0.2 输入与偏好 | 逐平台确认连续点击、拖动／长按阈值、滚轮、caret、滚动条、动画、对比度、透明度、文字缩放的公开来源与更新通知 | 已知值／未知值、单位、版本要求与回退明确；Windows AutoHideScrollBars、GTK 4.18 等基线问题有具体结论 |
| S0.3 原生文本菜单 | 用一个真实自绘编辑宿主验证标准菜单、选择、焦点和编辑命令；分别核查系统默认菜单及第 5 节文本服务 | 标准原生菜单能走同一编辑模型；额外服务按项目列出能否接入及后续所属批次 |
| S0.4 原生拖放 | 最小文本 source／target，验证同窗口、同程序两个窗口、外部进程及 native tracking 中的 Drop／取消／关窗 | owner 可推进，数据和回调寿命清楚，同程序 Drop 不因同步等待而死锁，Copy／Move 的完成边界明确 |
| S0.5 原生 accessibility | 三平台最小按钮、输入、焦点、虚拟条目；同步 getter／动作／Realize／关闭及原生窗口树衔接 | 外部客户端实际读写；macOS／UIA 的返回与线程合同明确；Linux 在 GTK 公共接口与 GIO／GDBus 路线之间形成可实施结论 |

Linux 原型必须验证 Action、GrabFocus、EditableText 和原生树衔接，不能以 `GtkAccessible` role 可见作为通过。若 GTK 公共接口无法闭合，验证直接 AT-SPI 子树与 GTK 窗口／菜单的衔接后选一条正式路线；不保留两个表达同一子树的生产 provider。两条路线均未通过时记录核心能力未完成并修订该平台方案，不能降为可选功能来关闭计划。

原型只补必要的实际消费者和原生测试辅助，不建新的演示框架、RPC、轮询循环或通用同步调度器。同步查询与动作的 spec 先明确边界，再实现实验；失败结论同样应收束到明确的平台问题。

**通过条件：** 每个后续批次所需结论独立可用；S0.3 的高级菜单服务和 S0.5 的 Linux 问题不阻塞无关的点击修复、滚动条或 macOS 语义工作。

### S1 系统偏好、点击计数与公共输入

**主要范围：** Window 共享输入／设置与三个 native 后端、UI 根、style／theme 的实际消费者。先改 Window、UI、Style／Theme spec。

- [ ] 提供不可变的系统偏好值和 owner 变化通知，区分未知与明确关闭；落实根继承、控件覆盖与 `FollowSystem`，不按主题名称判断 OS。
- [ ] 接入常显／自动隐藏条、减少动画、高对比度、减少透明度、文字缩放及 caret 闪烁／宽度；保证设置在没有 accessibility 客户端时也生效。
- [ ] 明确点击距离、拖动／长按阈值、物理／逻辑长度、caret 整周期／切换间隔的单位转换。滚轮保持行／像素、相位和系统已应用的方向设置。

Linux musl 目前不交付 GUI，不纳入本轮 GUI 目标。特定硬件确实不提供某个手势或触觉能力时记录实际能力；开发机暂缺设备则是验证尚未完成。已有成功结果按覆盖范围复用，不为同一 UI 行为机械重复所有平台／主题／输入的笛卡尔积。

本矩阵用于功能验收。三级的配色微调只在 macOS 验证，不追加 Windows／Linux 配色回归，也不重新打开已通过且未受影响的功能检查。

### 6.2 测试层次

- 普通 Cone 测试：配置解析、计数／状态机、时间边界、词／范围映射、编辑事务、数据级查找、语义身份／合并／资格与几何计算。
- 现有实窗测试及必要 native 辅助：原生事件、IME、菜单、触摸路由、Accepted／Discarded、焦点、设置通知、tracking 与关闭。
- 独立外部进程：跨程序拖放、AX／UIA／AT-SPI 查询和动作、客户端晚释放引用、真实通知与结果。
- 真实人工／工具交互：触屏／触控板、VoiceOver／Narrator／Orca、跨显示器、可发现性，以及结构化工具和截图工具完成实际任务。

先对受影响 Scoop 文件执行既有 fmt／check，再运行对应 release tests／build／native 场景；实际修改 Rust 或 Python 时遵守仓库相应 fmt／lint 命令。使用显式准备的开发 sysroot 和共享 Cone cache，普通测试不逐项复制或重建系统库；保留源码、工具和原产物，不用移除它们验证缓存。GC stress 只用于确实改到 GC／callback 保活的专项问题，不成为全量 UI 验收模式。

纯文档更新只核对链接、引用和范围一致性。生产代码实施后按实际变化扩大测试；编译器／CLI／ABI 未改动时，不因此新增整套编译器全量验收。
