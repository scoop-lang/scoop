# Markdown 本机交互测量

本轮按用户要求只测本机 release。测试使用公开 `markdownEditor` 组件、同一文档和后台解析器；普通文字、源码与原位扩展输入都通过真实 macOS `NSTextInputClient`，逐次检查源码长度与 UTF-8 光标位置。性能数字是指定设备与语料上的观测值，不作为库 API 的运行时限制。

## 语料和环境

混合语料取当前仓库的 `SCOOP-IMPL-SPEC.md` 与 `SCOOP-SPEC.md`，补充少量中英文、引用、嵌套列表、任务、图片与行内公式。重复到目标大小后，在下一个物理行边界结束，保留 UTF-8；报告实际字节数。1／5 MiB 分别测源码、所见即所得、双栏左侧输入和双栏右侧输入；20 MiB 只观察源码／富文本的增长趋势。

专项包含约 130 KiB 的单一中英段落、130,000 字节无空格文本、100,000 行代码的原位源码、3,000 行表格，以及 5 MiB 文档中的原位图片源码。图像和公式以当前未配置外部 renderer 的回退展示参与混合语料；外部工具的冷启动与渲染耗时不混入文本输入指标，其实际适配与像素／资源合同已有独立测试。

条件固定为 1,200 × 800 逻辑像素、16px 正文字号、1.5 行高，Roboto 与 Noto Sans CJK 测试字体，默认浅色主题、默认 Markdown／代码高亮和单个解析 worker。换宽在 900 与 1,200 逻辑像素间交替。程序启动、语料文件读取和语料拼接分别处理，不计入文件内容交给编辑器后的首视口时间。

## 指标定义

- **首个可编辑视口**：从重载文档并请求目标模式／焦点，到对应帧已提交且原生输入可用；富文本侧还要求当前结构已经参与该帧。
- **输入 P50／P95**：从调用真实原生文本输入，到包含新正文／caret 的帧得到 `FrameSubmission.Accepted`。以原生 presentation 计数确认绘制提交；这不包含 GPU 完成或屏幕扫描显示时间。
- **原生调用成本**：同步原生输入调用的耗时；**排版＋scene 成本**是该帧子视图测量和绘制命令准备的耗时。它们用来区分编辑、绘制工作与帧调度，不能替代输入到帧的指标。
- **预览收敛**：最后一次输入到包含同一 revision 完整解析结果的帧提交。只观察 parser Ready 不视为收敛。
- **滚动**：每次推进 120 逻辑像素，报告请求到对应帧的分位数、排版／scene 成本和超过 16.67ms 的次数。超过该值是本次操作超出 60Hz 时间窗，不等同于 GPU 丢帧计数。
- **换宽**：6 次请求到匹配新宽度帧提交的 P95。

普通混合语料先进行 4 次预热输入，再记录 64 次；20 MiB 和大块专项使用较少样本，仅作增长与边界观察。结果不通过重录期望或删除慢样本判为成功；功能断言检查实际输入和帧，而时间原样报告。

## 复现

构建与打包沿[原生窗口说明](../../../sysroot/src/scoop.ui.markdown/tests-cones/editor/README.md)。从仓库根运行，使用新的空事件目录：

```sh
mkdir /tmp/scoop-markdown-performance-events
open -n -W \
  --env SCOOP_TEST_RUN_DIR=/tmp/scoop-markdown-performance-events \
  --env SCOOP_MARKDOWN_PERF_REPOSITORY="$PWD" \
  '/tmp/scoop-markdown-editor-app/aarch64-apple-darwin/prebuilt/org.scoop.tests.markdown-editor/app/Scoop Markdown Editor Verification.app' \
  --args --scoop-test-filter MarkdownPerformanceWindowTests
```

默认执行全部语料；可额外传 `--env SCOOP_MARKDOWN_PERF_CASE=mixed-5-side-rich` 等精确名称，只重跑指定场景。`PERF_BEGIN`、`PERF_VIEWPORT`、`PERF_CONVERGED` 和 `PERF_RESULT` 写入 `0.stdout`。必须核对完整 begin／end／complete 及空 failures；保留结果概要后清理临时程序与原始日志，正常 Cone 构建缓存保留。

## 本轮结果

2026-11-15，Apple M3 Ultra、512 GiB 内存、macOS 27.2.1（26B131）、aarch64-apple-darwin。工具链为 `scoop 0.0.0-dev (6289e706e3+unit-statements)`；库基线为 `3057db363e`，本批仅增加测量与材料。本轮观察到约 60Hz 的提交节奏。

仓库原始两份文件分别为 641,186／546,814 字节，连同中间分隔共读取 1,188,002 字节，本次读取约 14.7ms。混合语料实际大小为 1,049,035／5,243,799／20,971,697 字节。最终一次完整运行的 17 个场景、676 次原生输入（含预热）和 464 次滚动全部通过，事件协议完整且 failures 为空，整组约 41.9 秒；这组总耗时不作为单次交互指标。

### 增长与大块边界

| 场景 | 首视口 ms | 输入 P95 ms | 排版＋scene P95 ms | 预览收敛 ms | 换宽 P95 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 20 MiB：源码 | 110.6 | 31.3 | 0.6 | 3136.0 | 19.9 |
| 20 MiB：所见即所得 | 1764.3 | 18.8 | 0.6 | 3167.1 | 37.1 |
| 133,127 B 单段：源码 | 150.9 | 44.9 | 38.8 | 101.5 | 57.0 |
| 133,127 B 单段：富文本 | 213.9 | 100.3 | 69.0 | 165.9 | 96.4 |
| 130,000 B 无空格文本：源码 | 44.6 | 26.2 | 23.6 | 25.1 | 24.3 |
| 130,000 B 无空格文本：富文本 | 72.9 | 48.6 | 24.4 | 65.6 | 55.9 |
| 100,000 行代码：原位源码 | 831.5 | 17.5 | 1.1 | 1351.7 | 22.1 |
| 3,000 行表格：富文本 | 82.9 | 22.1 | 0.7 | 97.9 | 23.7 |
| 5 MiB 文档：原位图片源码 | 462.9 | 20.9 | 0.6 | 500.1 | 27.8 |

- 20 MiB 的文字输入仍局部处理，完整预览收敛增长到约 3.2 秒；本轮使用合并请求后的后台全文解析，没有把该规模声明为与 1／5 MiB 相同的收敛目标。
- 长单段保留完整 shaping，133,127 字节的富文本输入 P95 约 100ms，换宽约 96ms；130,000 字节无空格文本也明显增加成本。它们不能代表常规块分布的大文档，当前同样不具有恒定输入延迟。本轮公开这个限制，不为远超仓库常见段落规模的样本追加新的跨线程排版 API。
- 十万行代码按源码物理行投影，输入 P95 约 17.5ms；完整解析与高亮收敛约 1.35 秒。三千行表格和大文档中的行内图片源码分别约 22.1／20.9ms，证明原位编辑没有按键重建整篇视图。
- 长段样本的首个可编辑文本叶预先使用合法的逗号转义，避免把结构化编辑允许的源码规范化当作额外输入；正文含义和格式保持，后续每次仍严格断言新增字节和光标。测量程序显式启动共享解析器，并以解析状态参与帧观察，避免把纯源码模式的未启动状态或较旧帧当作收敛结果。

本轮没有改变渲染资源的线程归属、把段落任意切段、隐藏正文或禁用富文本。需要更长单段、更快的巨大代码高亮或 20 MiB 结构收敛时，应以这些明确数据提出后续优化，不由此扩充本轮的具体 Markdown 扩展集。
