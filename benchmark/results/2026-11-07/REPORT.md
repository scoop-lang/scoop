# 第二轮本机基准：与 2026-10-29 对比

2026-11-07，同一台 Apple M4 Pro（14 核，64 GiB），方法、源码、规模与 Go（go1.27.3）、
GraalVM（21.0.12+7.1）版本均与 [第一轮](../2026-10-29/REPORT.md) 相同，只更换 Scoop 工具链。

工具链由 `scripts/package_toolchain.py` 从 `2bd06a47b` 重新构建全部组件包（LLVM 22.1.8、
LLDB、native 资源、runtime、两个 Darwin 目标的系统 `.slib`），解压到全新的 `~/.scoop` 并运行
post-install；所有 Scoop 应用由 `~/.scoop/bin/scoop` 构建。版本后缀 `+modified` 来自工作区中
两个未跟踪的文档目录，不涉及代码。上一轮为 `ae13036d9`，期间合入 38 个提交。

正式测量 240 个进程、1200 个批次，全部通过缩小输入与完整规模校验；另对 6 项做 7×300 ms 的
[定向复测](repeat/measurements.json)。数据见 [TABLES.md](TABLES.md) 与 [图](relative-time.png)。

## 环境整体变快

这一轮 Go 与 Java 在多数项目上也快了 1–7%（例如随机索引追逐四种实现都快约 6.5%），
来自机器状态差异而不是这些实现本身。因此下面以 “Scoop / Go 比值” 判断 Scoop 自身的变化，
小于约 5% 的单项变化不视为改进。

## 运行时间：明确变化

单位 ms / kernel；“复测”为定向复测的中位数。

| 工作负载 | 10-29 Scoop | 11-07 Scoop | 复测 | Scoop/Go 10-29 → 11-07 |
|---|---:|---:|---:|---:|
| Unicode 标量遍历 | 1.089 | 0.842 | 0.892 | 3.54 → 2.73 |
| 值记录数组 | 0.441 | 0.375 | 0.389 | 1.98 → 1.69 |
| 浮点数组 | 0.894 | 0.771 | 0.798 | 1.84 → 1.60 |
| 引用记录数组 | 2.110（复测 2.569） | 1.911 | 1.927 | 1.11 → 1.02 |

- Unicode 遍历仍有进程间双峰：多数进程约 0.82–0.89 ms，个别进程停留在旧水平（1.03–1.14 ms）。
  改进方向确定，具体幅度约 18–23%。与 Graal JIT 相比仍慢约 7 倍。
- 引用记录：两次测量都稳定在约 1.92 ms，基本与 Go 持平；上一轮的大幅进程间波动
  （2.10–2.99 ms）消失。GC 诊断中分配量与回收次数不变（11.53 MB/call，6 minor + 3 full），
  八次调用的总暂停从 5.15 ms 降到 3.80 ms。
- 值记录、浮点数组的分配量与回收次数不变，full GC 暂停分别从 0.63／0.58 ms 降到 0.18／0.46 ms；
  耗时改进大于暂停变化，还包含代码生成方面的差异，本轮未做汇编归因。

## 运行时间：没有实质变化

- 整数依赖链、Mandelbrot、条件归约、随机访存、快速排序、逃逸对象、二叉树、
  十进制格式化、多核 1／4 worker：Scoop/Go 比值变化在 ±5% 以内。
- 动态接口调用：1.246 → 1.207 ms，仍约为 Go 的 3.2 倍。
- 哈希表：4.747 → 4.729 ms，Scoop/Go 比值 1.35 → 1.38。HashMap 分组探测（#94）使
  每次调用的分配量从 7.34 MB 降到 6.55 MB、八次调用 full GC 从 4 次降到 3 次，但这一负载的耗时没有改善。
- 十进制解析：3.725 → 3.408 ms，但 Go 同期快 5.9%，比值 3.06 → 2.98，仍是最大差距之一。
- 动态容器增长：仍为双峰（复测进程 0.39 与 0.57–0.59 ms 并存），与上一轮一样不稳定。
- 8 worker：0.897 → 0.950 ms，复测 0.937 ms，在上一轮进程范围（0.889–0.966）内，不视为回退。

## 启动、内存、体积和构建

| 指标 | 10-29 | 11-07 |
|---|---:|---:|
| Scoop 空进程启动／退出中位数 | 6.03 ms | **3.74 ms**（Go 3.64 → 3.08） |
| Scoop 空进程峰值 RSS | 5.7 MiB | **3.4 MiB** |
| Scoop 各工作负载峰值 RSS | — | 普遍下降约 2.3 MiB |
| Scoop 可执行文件 | 2.12 MiB | **1.27 MiB**（Go 2.38 MiB 不变） |
| Scoop 应用首次构建（三次中位数） | 4.978 s | **2.897 s** |
| 同上，构建进程峰值 RSS | 1.33 GiB | 1.12 GiB |
| Scoop 输入不变再次构建 | 0.019 s | 0.020 s |

启动时间、基线 RSS 与文件体积的下降在所有工作负载上同时出现，与 GC root map 压缩、
移除逐 site runtime 注册（#101）及 slib／编译速度改动（#87、#88）的方向一致；本轮没有做逐项归因。
应用首次构建仍比 Go（0.103 s）慢一个数量级以上。

## 仍然最大的差距

按 Scoop/Go：动态接口调用 3.2×、十进制解析 3.0×、Unicode 遍历 2.7×、浮点数组 1.6×、
值记录 1.7×、动态容器 1.45×、哈希表 1.4×。与上一轮建议的优化方向一致，只有引用记录已基本追平。

环境说明同上一轮：共享桌面环境，未绑核、未锁频，结果为描述性比较，不作统计显著性声明。
